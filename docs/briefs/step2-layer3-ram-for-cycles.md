# Plan: step 2, layer 3 - trading RAM for cycles

**BUILT** (2026-10-17): items 1, 3 and 4 built; 2 built for the player in layer 4; 5 set aside; 7
built in layer 4; 6 built differently in layer 4 (decision 39); 8 still open (PLAN.md). What landed: "Landed" at the end.

KC, 2026-10-17: "we should never be waiting for the vsync when there is work to do", and the
memory map shows room to spend. **The aim: no late passes.** Every pass's work inside 2 fields
(79,872 cycles), by doing work ahead of time (in the wait, or at build time) and spending RAM to
make the run-time work cheaper. Order agreed with KC: **1, then 3, then 2; 4 as well.** 5 and 6
are for later, 5 needs a decision first.

  144 of 599 late** (39, 33, 16, 19, 36, 1, 0).
- An average pass (seed 1, 81,848 cycles): **waiting for the flip 27,775 (34%)**; drawing sprites
  15,248; deciding what to redraw 9,718; collisions 6,859; putting backgrounds back 6,767; scenery
  5,668; the rest of the logic 7,973; interrupts 1,840.
- 214 of the 223 late passes write a scenery column: when the view moves every mover moves on the
  screen, so every mover is redrawn (249 bytes drawn against 97 on a pass that does not scroll),
  and the column is built and written as well.
- A scrolled column (holding RIGHT, 278 scrolls): built 10.0k (clear 1.3k, stepping the 8 layers

## RAM to spend (the build's listing, `ffda286`)
Bank 4: 2,051 free (1,256 of it under ANDY). Bank 5: 3,485 free, and 4,089 more after start-up
(its copy of ANDY's sprites). Bank 6: 2,699. Bank 7: 2,285. Main RAM: 197 at `&333B-&33FF`;
894 at `&0982-&0CFF` and 16 at `&D2-&E1` that nothing in the source names (check at run time
before using). ANDY: 7. HAZEL (8K) unused, but paging it in hides the MOS ROM the scroll reads.

## The items
1. **Build the next column in the wait.** `wait_for_flip` spins 27.8k cycles a pass on average.
   When a pass has scrolled, the next wait builds the following column for the same direction:
   the 8 layers' walk and unpack, run on the real state, into `column_buffer`, then the state put
   back as it was, and the state the walk left kept. The real scroll then checks the prebuild is
   for its direction and starting viewport, and if so skips the clear, the walk and the unpack,
   installs the kept state, and adds the ground and the edge movers as now. Only when the time to
   the flip is enough (the User VIA T2 raster clock gives the field's position); never on a late
   pass. Every zero-page byte the walk writes that the logic later reads must come out as the real
   walk leaves it: find which with a run-time check before trusting it. Expect ~7k off every
   scroll pass (a simulation on `53076ff` of only the pixel part, 4.8k, moved for free: late
   passes 298 to 228 on seed 1, 187 to 141 holding RIGHT). RAM: ~180 bytes of state copies.
2. **Compiled sprites.** The most-drawn mover sprites as code: per byte
   `LDA (s),Y : STA (v),Y : AND #m : ORA #p : STA (s),Y : DEY` (21-23 cycles, against 37-40),
   per-column bookkeeping decided at build time, one save record a part. Generated by
   `tools/sprites.py`; in banks 5-7, called through a small main-RAM stub that pages the bank
   (bank 4 holds the renderer). ~13 bytes of code a sprite byte per flip: all 6,867 bytes would
   need ~180K, so first **measure which sprites are drawn** and compile the player's frames and the
   commonest enemy frames. Expect drawing 15.2k to ~8k a pass, putting back 6.8k to ~5k, more on
   late passes (250-400 bytes).
3. **No copy, no rescan.** (a) Build the column into one of two buffers the renderer writes
   from, so `history_push` is a pointer swap: -2.5k a scroll, and `write_column` a cycle a byte
   cheaper from main RAM. Needs ~400 bytes of main RAM (`&0982-&0CFF` if it proves unused).
   (b) `unpack_scenery_loop` ends at `move_to_next_column` with the next column's address, which
   is thrown away; keep it per layer and the forward walk need not scan the column again: most of
   `find_end_of_column_loop`'s 1.1k, no RAM.
4. **Tables for arithmetic.** Character-row offsets (`&280` x n) for `raise_address`,
   `world_of_address`, `up_a_cell` and the logic's `subtract_Y_rows_from_screen_address` (435 a
   pass); a multiply table for `multiply_A_by_X` (290 a pass); the ground's four textures as
   columns (0.5k to ~0.15k a scroll, and the way to fix BUGS #1 in layer 5 - the texture must stay
   the one the build makes today until then). ~1.5k a pass in all.
5. **Later, needs KC: run the next pass's logic in the wait.** With two screens the render cannot
   start until the last frame is shown, so the wait can only go to work that is not drawing. The
   largest such work is the next pass's logic: the renderer would draw from a snapshot of the
   movers (~300 bytes) while the logic runs a pass ahead. A pass would then cost the larger of its
   logic and its render, not their sum, and nearly every late pass would go. The cost: input shown
   one frame (40 ms) later than now - a change to how it plays, so KC's decision. Layer 4 (50 Hz)
   changes the pass structure, so decide this with layer 4 in view.
6. **Later: scenery runs translated at build time.** Each run stored with its pixel byte and kind
   (skip, fill, merge) already decided: about half the 3.3k unpack, for ~25% more scenery data
   (banks 6 and 7 may not hold it).

7. **Later (KC): the front end's music compressed** with ZX02 (the kit's `tools/zx02.py`): the title
   music (3,584 bytes) and the high score music (384) are needed only on the front end, so they
   can be kept packed in bank 5 and unpacked when the front end starts, into RAM the front end
   does not use. The music must stay page-aligned and is read by its event handler with bank 5
   paged, so the buffer must be main RAM (a save arena, the game's tables) - to be found. Frees
   RAM, not cycles: room for item 2.
8. **Later (KC): music in the game**, new, once 25 Hz holds comfortably with room to spare. A
   change to how it plays: a decision when it is built.

Not doable: the world as pixels (7,485 x 200 bytes); a clean background copy in place of save
blocks (16K a screen); the mountains baked in (they are the MOS 3.20 ROM's bytes at `&C300`: a
deviation on any other MOS).
